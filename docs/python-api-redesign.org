#+TITLE: Python client v2: a redesign sketch
#+OPTIONS: toc:2 num:nil
#+STARTUP: showall

Status: draft. This sketches the second generation of switchyard's
Python client. The first generation grew feature by feature while we
built end-to-end tests for downstream applications (power controllers,
battery schedulers, and other apps built on the frequenz SDK). Those
tests work, and they taught us where the seams are. This document names
the seams and the shape of the fix.

* Design principles

- *Typed values everywhere.* Quantities (~Power~, ~Energy~,
  ~Percentage~) at every boundary. No bare floats, no unit strings.
- *Intent over mechanism.* A test says what should happen (~drive~,
  ~status~, ~command~, ~expect~), not which endpoint to hit.
- *One concurrency model.* The core is async. Sync is a thin facade at
  the outermost layer, never a layer in the middle.
- *Metrics are data, not methods.* Adding a metric must not mean
  writing four new methods with eight copied keyword arguments.
- *A typed wire protocol.* The client never generates Lisp source as a
  transport. Lisp stays what it is good at: the human config and
  scenario layer.
- *Errors are exceptions.* Every rejected operation raises, with the
  server's reason attached. No silent no-ops, no ~ok: false~ payloads
  the caller must remember to check.

* What v1 got right (keep the surface)

These parts carried real integration suites well. v2 keeps their
*shape*; only the plumbing underneath changes.

- The topology builders (~sw.grid(...)~, ~sw.meter(...)~, ...) that
  read like the topology they build.
- ~launch()~ / ~connect()~ with ephemeral ports, the endpoint
  handshake, and context-manager teardown.
- The intent split on component handles: ~.command()~ goes through the
  real gRPC gateway (and can be rejected, like production);
  ~.drive()~ / ~.status()~ are test-side stimuli.
- Settle-aware assertions: ~eventually~ / ~always~ / ~once~ with typed
  matchers (~approx+tol~, ~within~, ~max~, ~min~).
- Formula reads as ground truth (~grid_power~, ~battery_power~, ...).
- The pytest plugin and the scenario DSL.

* The three seams

** 1. The concurrency sandwich

v1 stacks three regimes: a background asyncio loop owned by the gRPC
facade, worker threads for reads (so async assertions do not stall the
caller's event loop), and the caller's own loop. It works, but the
bugs we fixed lived exactly here (blocking reads on the loop,
check-then-insert races once reads became multi-threaded).

*Target:* an async-native core.

- ~switchyard.aio.Site~: every read, write, and wait is a coroutine.
  HTTP via an async client; the gRPC client used natively on the
  caller's loop — no background loop, no worker threads, no locks.
- ~switchyard.Site~: a thin sync facade over the async core for REPL
  use and simple scripts. It owns the one place where a loop is run.
  Async test code never sees it.

** 2. The per-metric method explosion

v1 hand-writes one method per metric per surface
(~ComponentExpect.active_power~, ~.soc~, ~MicrogridExpect.grid_power~,
...), each repeating the same matcher keywords. Symptoms: pass-through
wrappers, a *reduced* keyword surface on the cumulative metrics
(retyping fatigue), and every new metric costing four methods.

*Target:* one metric model, one assertion engine, and *signals* as the
surface.

- A ~MetricSpec~ describes a metric: name, quantity type, and *kind* —
  ~INSTANTANEOUS~ (power, SoC) or ~CUMULATIVE~ (energy).
- One engine consumes a bound metric and the matchers; the kind picks
  the semantics (settle vs one-shot).
- The public surface is the *signal*: one object per observable
  quantity, with up to three verbs — ~read~ (returns the plain
  quantity; raises ~NoSample~), ~expect~ (takes exactly one typed
  ~Matcher~: ~near~/~between~/~at_most~/~at_least~), and ~set~ where
  the simulator allows it. Capability lives in the type: a driven
  signal (a meter's power, a battery's SoC) has ~set~; a measured one
  (an inverter's power, the site's ~grid_power~) does not; a
  cumulative one's ~expect~ has no hold window. Misuse is a type
  error, not a runtime branch.
- The topology builders are the identities — and, once ~aio.launch~
  binds them, the live handles: ~LOAD.power.set(...)~,
  ~BAT.soc.expect(...)~. Site aggregates are signal attributes
  (~site.grid_power~).
- Naming rule: every ~*_energy~ aggregate is the time-integral of its
  paired ~*_power~ — a *flow*. Stored energy is component *state*
  (~BAT.stored_energy~, from SoC and capacity), never an aggregate, so
  "battery_energy" always means flow through the pool.

** 3. Lisp-by-string as the wire format

v1 assembles Lisp source with f-strings and posts it to ~/api/eval~,
which reports interpreter rejections as ~ok: false~ JSON. Escaping and
number formatting become client bugs; errors become a contract the
caller must remember to check.

*Target:* a typed control API.

- The server grows a small JSON control surface for everything
  programmatic: component stimuli (drive/status), topology edits,
  scenario definition and runs. Validation errors come back as
  structured errors; the client raises typed exceptions.
- ~/api/eval~ remains as the escape hatch, and the Lisp layer remains
  the human surface: config files, the scenario library, the REPL.
- Until the control API lands, the eval path stays behind one
  choke-point function that checks ~ok~ and raises — never scattered
  call sites.

* Target layout

#+begin_example
switchyard/
  metrics.py       MetricSpec, MetricKind, BoundMetric, the catalog
  assertions.py    the one kind-aware assertion engine
  aio/             async-native core (site, transports, scenarios)
  _facade.py       sync Site wrapping aio.Site (the only sync/async seam)
  build.py         topology builders (unchanged surface)
  pytest_plugin.py fixtures on top of the facade or the aio core
#+end_example

Downstream test suites (any SDK app: controllers, schedulers,
optimizers) should only ever import the top-level package.

* Scenarios speak signals too

The scenario DSL is the same testing vocabulary at a different time:
a *check* is an ~expect~ scheduled at a point in the run, and a *cue*
is a ~set~ scheduled at a point in the run. So the DSL takes signals
and matchers, not raw ids, a ~Metric~ enum, and a keyword bag:

#+begin_example
scn = sw.Scenario("cloud-fade", length=timedelta(minutes=4))
scn.at(timedelta(seconds=30), pv.sunlight, percent(20))     # cue
scn.check(timedelta(seconds=110), inv.power,
          sw.near(MW(1.5), tol=kW(300)))                    # check
scn.check(timedelta(seconds=110), bat.soc, sw.at_least(percent(40)))
#+end_example

- A cue targets a *settable* signal; a check any component signal.
  The capability typing carries over: cueing an inverter's power is
  a type error, exactly like ~.set~ on it.
- Matchers are shared with ~expect~, so a live assertion and a
  scenario check read and fail the same way.
- Signals carry their *identity* (component + metric) without being
  bound: properties never raise; only calling a verb on an unbound
  builder does. Scenarios are authored before launch.
- The DSL still renders ~(define-scenario ...)~ Lisp underneath; the
  typed scenario wire format remains phase-3 work. Raw ~cue()~ /
  ~drive_form()~ escapes stay for anything not modelled.
- Server gap closed alongside: ~set-battery-soc~ joins the cue
  vocabulary (the control API's SoC teleport, callable from Lisp).
- Known limitation: checks are per component server-side; aggregate
  checks (grid power) are follow-up work with the typed wire format.

* Migration plan

- *Phase 1 — metric model (compatible).* DONE. ~MetricSpec~ /
  ~BoundMetric~ landed and every existing ~expect~ method routes
  through the one engine. Public surface unchanged, except the
  cumulative metrics gained the full keyword set they were missing.
- *Phase 2 — async core.* Core DONE: ~switchyard.aio~ is async-native
  end to end (no background loop, no worker threads, no locks), with
  *signals* as the assertion surface. REMAINING: reimplement the sync
  ~Site~ as a facade over the aio core so the duplicated transports
  can go; until then the sync client keeps its own.
- *Phase 3 — typed control API (server + client).* Stimuli DONE:
  ~POST /api/component/{id}/status~ and ~/drive~ (plus per-mg
  variants) with structured 400/404 errors; both clients use them for
  ~status()~ / ~drive()~ constants, and rejections raise
  ~ControlRejected~. A ~RawLisp~ drive (lambda / symbol) still rides
  ~/api/eval~ through the raising choke point, by design. REMAINING:
  typed scenario definition/runs and topology edits.

Each phase must keep the downstream integration suites green — they
are the acceptance tests for this redesign.

* Non-goals

- No new assertion semantics. ~eventually~ / ~always~ / ~once~ cover
  what real-time tests need; v2 only changes who owns the dispatch.
- No ORM-style topology mutation API. Topology edits stay explicit.
- No promise of API stability before the redesign completes; the
  package stays 0.x until phase 3 lands.
